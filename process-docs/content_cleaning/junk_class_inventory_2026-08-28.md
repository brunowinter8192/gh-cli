# Junk Class Inventory — github_issues corpus (2026-08-28)

Ad-hoc read-only scan of the live `github_issues` MD corpus, taken before any build-log work
started. Purpose: establish what noise classes actually exist across the whole corpus rather than
the single repo the 2026-06 cleaning pass happened to sample. Only one of the classes below
(BUILD_LOG) was acted on; the rest are recorded here so the measurement is not lost.

Corpus at scan time: **844 MDs, 6,950,392 chars, 19 repos** (`data/documents/github_issues/`).
It grew to 873 during the session, from a parallel session's `index_issues` run — that addition
did not change any figure below, since the 30 added files contain no matched noise.

## Why the 2026-06 measurements no longer covered the corpus

The 2026-06 pass measured 103 MDs, all from `anthropics/claude-code` (avg 6,061 chars/file).
By 2026-08 the corpus held 19 repos with wildly different noise profiles — `pyobjc` averages
46,598 chars/file, 7.7× the corpus mean, from 8 files carrying 5.4% of the whole corpus. Classes
A through G below simply do not occur in claude-code issues, which is why the earlier pass never
saw them.

That earlier pass also recorded an explicit decision *against* length-based stripping, on the
evidence that shell/code blocks in claude-code issues are signal (repro steps, evidence tables).
That decision remains correct for what it measured; it does not generalize to a 1,610-line
`copying … -> build/…` sequence.

### Detail worth keeping

- **A — BUILD_LOG.** `pyobjc__34.md` is 198,266 chars of which one fenced block is 197,174 —
  the file is 99% build log. Corpus-wide, 1,326 lines of shape `copying PyObjCTest/<f> -> build/<p>`;
  `clang: warning: argument unused during compilation: '-mno-fused-madd'` appears 97× in one file.
- **B — DEBUG_STREAM.** `debug(app): mailbox message=redraw_surface` 96× in `ghostty__10406.md`,
  47× in `ghostty__10379.md`. `pw:channel:event {` 26× in `playwright__13156.md`. MinerU files
  carry loguru lines (`2024-07-17 23:38:42.992 | INFO | magic_pdf...`).
- **D — JSON_DUMP.** Whole GitHub API responses pasted into issue bodies —
  `"repository_url": "https://api.github.com/repos/microsoft/playwright"` 30× in one file.
- **E — LONG_FLAG_LINE.** 43 files, only 111 lines, but 174,974 chars: single lines of
  1,500–4,000 chars listing ~40 Chromium `--disable-*` flags. These pass the existing
  `\S{1000,}` net because the flags are space-separated. Near-identical across every playwright
  issue, and repeated within a file once per launch attempt.
- **F — TRACKER_MIGRATION.** Every pyobjc issue opens with
  `**[Original report](https://bitbucket.org/ronaldoussoren/pyobjc/issue/N) by <name> (Bitbucket: …, GitHub: …).**`
  followed by a `----------------------------------------` rule. Small in chars, but it is the
  first content chunk of the file, so it pollutes the embedding a query most often lands on.
- **G — AUTOMATED_COMMENT.** The literal marker `(automated comment)` in 5 of 8 pyobjc files:
  `Removing version: 3.0 (automated comment)` and equivalents for 3.1, 2.4, 2.5. The author is
  the maintainer's human account, so the existing `Author` ends-with-`[bot]` filter cannot see
  them. The text is self-declaring, which makes it a safe anchor.
- **H — EMPTY_TEMPLATE.** `_No response_` 313×, `No comments on this issue.` 130×.
- **I — STRUCT_RESIDUE.** Emitted by `build_issue_md` / `get_issue_comments`, not by GitHub:
  `--- Comment N ---` 4,573×, `# Comments on <owner>/<repo>#N` once per file, `Total: N comments`
  once per file. The 2026-06 pass judged this "not worth the false-positive risk"; at 844 files it
  is 2.5% of the corpus and 100% machine-generated by us, so the false-positive risk is nil.
- **J — cross-cutting detector, not a class.** 47 files contain a line repeated ≥5×; 2,137
  redundant lines = 115,180 chars (1.66%). Reliably points at B, C, D and E.

## The constraint every rule has to respect

`playwright__37199.md` (190,705 chars) contains a `ProtocolError: Protocol error
(Browser.getVersion): Internal server error, session closed.` plus a 20-frame stack trace through
`playwright-core/lib/server/…`. That trace **is** the retrieval target — a user hitting the same
crash searches for exactly that string. Across the corpus, 1,010 stack-trace lines in 66 files.

A rule may therefore not key on "looks like machine output". It has to key on repetition and
position within a block: the first lines of an error block carry the signal, lines 200–1,600 of a
`copying …` sequence do not. This is what the build-log detector's hard error/traceback exclusion
implements.

## Fenced-block measurement, and why it is only an upper bound

36.8% of corpus chars (2,556,448) sit inside triple-backtick fences; 69 blocks over 100 lines
carry 19.0% of the corpus and 13 blocks over 300 lines carry 10.7%. Hypothetical truncation of
every fence: 20 lines removes 23.7% (267 files), 40 lines 18.7% (162 files), 60 lines 15.6%
(111 files).

**Caveat that makes these numbers unusable as-is:** 15 of 844 files have an odd number of ```
markers, i.e. an unclosed fence. The parser then runs to EOF and counts too much as fenced. The
figures are an upper bound, not a measurement. They were not used for any decision — the build-log
detector works on line runs and ignores fences entirely.

## Scope decision

Only class A was implemented this session, by explicit instruction: measure everything, act on
one. Classes F and G remain the subject of the open goals that motivated the work. B, C, D, E, H
and I have no owner yet.

For any of them, the sequence that worked for A is the one to repeat: read real files to derive
the vocabulary, gate on a run/repetition property rather than on line appearance, dump the removed
text verbatim, read that dump in full, and let the corpus — not invented fixtures — decide. See
the revert entry in this area for what happens when that last point is violated.
